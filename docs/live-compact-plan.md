# SoL-Pi Live Compact 总方案：质量优先的高保留模式

状态：P0 已完成，P1 已在 `feat/local-context-policy` 分支实现并通过自动化测试（见 §13 实施记录）；P2–P5 尚未实现。未做全局安装，也未在真实 provider 上运行。最终优先级为 **AI 性能 > 用户体验 >> token 开销**；取代早期方案中以经济收益触发压缩的取向。

## 1. 目标与结论

用户希望：上下文较小时不处理；约 70% 开始维护；长任务尽量运行在 70–80%；token 费用不敏感，优先保留有用历史，避免原生压缩一次概括过多内容。

文中的 70%/80%、最近 3 轮和模型选择均为默认策略，不是写死的常量。可配置字段、建议默认值、合法范围与生效规则统一见 [配置规范](live-compact-config-plan.md)；实施配置、preflight 或示例时以该文档为准。

**结论：在 SoL-Pi 内增加显式开启的高保留模式，复用 ObservationPack 的归档/召回和 OCC 的压缩生命周期；不移植 DSH 后端，不修改 Pi 核心。**

新模式不是更积极的摘要器，而是以下控制链：

```text
完整会话历史与证据
    ↓
按当前模型窗口计量本次请求
    ↓
低于 70%：不新增收短决策
    ↓
达到 70%：进入维护，保护近期工作，观察本轮增长
    ↓
预计逼近/超过 80%：只收短足够数量的旧工具输出
    ↓
仍然过大：仅摘要必要的旧前缀，尽量保留约 70% 的有效上下文
    ↓
仍无法安全装入：明确暂停，不静默退回仅留约 20K 尾部的大压缩
```

70–80% 是正常工作目标，不是硬性下限或精确实时保证：

- 不填充无用内容来达到 70%；整条输出替换、摘要长度、调用配对边界可能让结果低于 70%。
- 在安全和信息保真允许时，尽量少移出内容，而不是尽可能压小。
- 用户消息、图片或一批必须保留的结果可能本身超过预算；必须支持暂停，不能承诺永不超窗且永不丢信息。
- “原文在磁盘上可召回”不等于“模型当前仍然记得”。关键事实保留和任务质量需要独立验收。

优先级：**AI 性能 > 用户体验 >> token 开销。**

- **AI 性能**：任务完成率、推理/代码正确性、长期约束与证据保留，不是单指生成速度。保留有用原文，也允许移出干扰性的冗余内容；上下文越长不自动代表性能越好。
- **用户体验**：前台响应、连续对话、少等待、状态清楚；以不降低任务质量为前提。
- **token 开销**：诊断指标，不是触发压缩、选择弱模型或缩短证据的理由。允许更丰富的摘录、较长摘要和额外质量核验。
- **不可交换的底线**：数据完整性、来源/授权边界及请求容量安全；任何优先级都不允许静默丢失证据或发送已知超限请求。

### 核心决策速览

| 问题 | 总方案决策 |
|---|---|
| 为什么维持 70–80% | 保留较大的有效工作集，不为省费主动压小 |
| 日常如何维护 | 本地代码局部收短旧工具输出，不每轮调用摘要 AI |
| 突然加入大量内容 | 每次请求独立准入检查，覆盖用户输入、附件与整批工具结果 |
| 何时调用摘要模型 | 只有局部整理不足或明确预测很快不足时，处理固定旧前缀 |
| 摘要模型怎么选 | 默认跟随工作模型；独立快速模型通过保真评测后可选，强模型核验后提交 |
| 后台摘要来不及 | 安全范围内继续工作；不能安全继续则等待/暂停，不换成更激进的压缩 |
| 如何防止旧快照覆盖新消息 | 只提交匹配来源哈希的旧前缀摘要，保留当前新尾部，重新检查预算 |
| 缓存命中低怎么办 | 接受一次性摘要的低命中，不维护整份影子对话来追缓存 |
| 原生压缩怎么用 | 新模式接管自动路径的范围；只摘要必要旧前缀，用户手动深压缩另算 |

### 2.3 P0 核验结论（Pi 1.5.2 源码，1.5.0 对应函数逐字一致）

每个工具轮之后的实际顺序：

```text
finishTurn → turn_end 边界（扩展）
→ prepareNextTurnWithContext → _compactBeforeNextAssistantResponse
     按 canonical 会话投影估算；超阈值则 _runAutoCompaction("threshold") → session_before_compact
→ turn_start → 排队消息入上下文
→ prepareRequest（canonical 投影；virtual model 路由后再查一次阈值）
→ streamAssistantResponse → transformContext（扩展 context 处理器）→ convertToLlm → provider
```

另有 run 结束后、提交 prompt 前的 `_checkCompaction`（含 overflow 恢复）。

结论：

1. 原生阈值检查使用 **canonical 投影**，不含 ObservationPack 在 `context` 中做的替换，并且早于 `context`。因此，单靠 `context` 收短无法阻止原生深压缩，必须在 `session_before_compact` 中协调。
2. `session_before_compact` 带 `reason`（`manual` | `threshold` | `overflow`）、`willRetry`、`preparation`、`branchEntries` 和 `signal`，可通过公开 API 区分用户 `/compact` 与自动触发。
3. 返回 `{ cancel: true }` 会使本次自动压缩失败并继续发送请求；这时请求必须由新模式自己的投影与准入检查保证安全。
4. 返回 `{ compaction: { summary, firstKeptEntryId, tokensBefore, details } }` 时，`appendCompaction` 直接采用扩展给出的 `firstKeptEntryId`。这是通过公开钩子实现“只摘要必要旧前缀、保留大尾部”的入口；P3 需加测试，防止切点落在工具配对中间。
5. 决策规则：`threshold` 时，若新模式投影在安全预算内，取消原生压缩；否则提供限域 compaction 或暂停。`overflow` 时保留原生恢复，除非能给出更保真且安全的限域结果。`manual` 尊重用户意图，不拦截。

## 3. 从 Live Compact 借鉴什么

参考快照：`dsh-live-compact` **1.1.5**，提交 `de72685288cd4e20e2b7e65b2b253b7d825cf41c`。[L1]

此次使用只读 `git ls-remote` 固定 HEAD，再读取固定提交的 README、`index.js`、`plan.js`、package 和 LICENSE。GitHub 匿名 API 曾返回限流；未更改认证配置。

| 参考机制 | 在 SoL-Pi 中的处理 |
|---|---|
| 轮后维护、增长预测、有限次局部整理 | 吸收；按模型比例和本轮实际结果决定，不搬固定 token 线 |
| 最近工具轮保护、调用结果配对 | 吸收；保护轮数可配置，默认最近 3 个完整工具轮 |
| 原文归档成功后才替换 | 吸收并扩展到摘要前缀归档 |
| 提交前重新检查所选区间、用户边界和配对 | 吸收；将会话/分支/模型/输入变化纳入失效条件 |
| 已处理区域不反复重写 | 吸收稳定决策；不强制使用“最新卡片以左永不再处理”的绝对地板 |
| 卡片标注来源，不把旧摘录当新授权 | 吸收；卡片仍保留为原来的工具结果角色 |
| 捕获游标、队列、分批让出事件循环 | 吸收；与已提交占位符的应用分开 |
| DSH 后端替换、preset patch、surface 日志事务 | 不移植 |
| 默认 20K 起点、32K 停止线、650K 小切停线 | 不移植；这些目标与高保留模式不同 |
| 基于文本规则提取事实、处理失败诊断 | 首版不移植；不依靠词表推断用户授权或事实真实性 |
| 按容量轮换备份 | 不照搬；首版不自动删除归档 |

`finishTurn` 已实现一次快照上的有限轮次维护；`commitSelectedSpan` 检查备份、区间变化和配对；`plan.js` 有完整工具轮与卡片覆盖检查。[L2][L3] 它也存在长 read 特殊处理等例外，不能将“所有最近 3 轮永不收短”视为其所有路径的统一保证。

只参考约束思想即可；若复制具体代码，保留 MIT 版权和许可证说明并登记来源。[L4] 不把 DSH 或其他移植项目的测评数字当作本项目收益。

## 4. 总体架构：一个决策者，一个工具投影写入者

> **P0 后的实现调整（Pi ≥ 0.87）**：局部整理不再写在 `context` 钩子里的临时投影，而是在公开的 `turn_end` 边界提交持久化的 `context_edit` 条目（见 §2.3）。这样，Pi 原生阈值估算、fork、tree 导航和恢复会话看到的是同一份收短后的上下文；原始条目保持不变，原文仍通过 ObservationPack 的归档和 `obs_recall` 召回。新模式下，ObservationPack 只提供归档与召回（`legacyProjection: false`），OCC 关闭经济触发（`economicCompaction: false`），由独立的 `extensions/live-compact/` 负责压力决策。下图中的“唯一工具投影写入者”因此对应为 Live Compact 的 `context_edit`。Pi 低于 0.87 时新模式保持不活动并提示，旧模式不受影响。

```text
Pi 会话树 / 新工具结果 / 模型与工具声明变化
                  ↓
        ContextBudget + BranchState
                  ↓
          LiveCompactCoordinator
          ├─ 未到水位：观察
          ├─ 局部整理：ObservationPack
          ├─ 摘要准备：SummaryPipeline（模型路由、核验、可选后台）
          ├─ 限域摘要：NativeCompactionAdapter
          └─ 不可安全继续：Pause + 明确原因
                  ↓
       单一 ObservationPack context 投影
                  ↓
        最终请求预算校验 + provider usage 校准
```

- ObservationPack 仍是工具结果投影的唯一写入者；就地修改 Pi 提供的消息副本，不重建整段消息、不改变角色/顺序/调用 ID。
- 新 coordinator 扩展现有 OCC 装配，不再额外注册一个竞争性的压缩插件。
- 新模式启用后，**OCC 的经济触发被替换为压力触发**；`update_plan` 仍提供任务边界与进度，不再是压力检查的前提。
- 复用 OCC 的停止活动 run、等待 settled、压缩完成后继续等生命周期；具体事件顺序需按目标 Pi 版本验证。
- 保留 Pi 原生手动 `/compact` 的用户意图；默认高保留保护针对自动路径。手动命令可能进行更深压缩，文档和状态中应明确。
- 新模式关闭时保持原有四机制行为，不能让新请求计数、摘要策略或日志格式意外改变 legacy 路径。

## 5. 水位、预算与状态机

### 5.1 统一计量口径

定义：

- `C`：本次实际路由模型的上下文窗口。
- `P`：预计本次发给模型的输入，包含系统提示、工具声明、摘要、当前工具投影和待发送消息；组件只计一次。
- `O`：与 Pi/provider 本次请求设置一致的输出预留，不自行更改模型配置；无法可靠获知时使用保守预留并标记估计。
- `M`：tokenizer 差异、图片估算和晚到声明等的自动安全余量，加上配置的 `budget.extraReserveTokens`；用户只能增加这部分额外预留。
- `H = C - O - M`：安全输入上限。
- 名义启动线 `S = startRatio × C`、回落目标 `T = targetRatio × C`、软上限 `U = ceilingRatio × C`；三个比例来自 `liveCompact.thresholds`，默认分别为 0.70、0.70、0.80。

只有 `U < H` 且留有足够操作余量时，70–80% 才完整可用。否则整体降低有效水位并明确显示原因，不维持名义百分比而挤掉输出预算。具体余量默认值在 P0 用目标模型与请求设置校准，不把任意固定值宣传为安全证明。

计量必须区分：

1. Pi canonical 会话投影的估计；
2. 应用本插件后、尚未发送的请求估计；
3. 最近一次 provider 实际 usage。

不能直接把上次 usage 当成本轮结果，也不能将“上次实际 input + 整份当前历史”重复相加。优先用可信快照加增量，再根据真实 usage 校准。未知值不是 0；模型切换、compact、分支切换、工具声明改变都使相应基线失效。

### 5.2 维护规则与迟滞

| 状态 | 行为 |
|---|---|
| `normal`：`P < S` | 不新增收短；继续应用已经持久化的决策 |
| `armed`：`S <= P <= U` | 开始候选/增长检查；不是每一轮都强行压回 70% |
| `maintenance`：本轮或近期增长预测将超过 `U` | 批量选少量旧结果，尽量回落至 `T`，达到目标即停 |
| `preparing`：预计局部整理不足，且后台功能已验收启用 | 只准备固定旧前缀摘要，前台仍使用当前有效上下文；不因草稿完成就立即替换 |
| `bounded-summary`：局部候选不足 | 摘要必要旧前缀，保留尽可能大的原样尾部 |
| `blocked`：无法满足安全预算 | 暂停并解释；保留原文和恢复入口 |

- 增长预测采用近期同类请求的保守增量信号；它只用于提前准备，不能限制未知工具的真实输出。
- 实际新增结果已到达时，以实际体积为准，预测不能覆盖真实检查。
- 冷却只防止没有新内容时反复维护，不能阻止越界保护。
- 第一次达到 70% 进入维护；例如当前 74%、预计下一批再加 9%，可以提前整理，而不等到超窗。
- 当已降到约 70% 且下一轮安全时，不因仍处于启动线附近而再次切割。
- 自动回落幅度超过本次需求时记录原因；不以“压得更小”作为成功指标。
- 80% 是软上限。已有可靠摘要正在准备、实际请求仍低于安全上限时，可短暂越过软上限以避免仓促损失信息；每次发送仍重新检查。持续超出时必须等待整理或暂停，不能将软上限变成无界积累。

## 6. 局部整理：保留信息优先，不追求最短卡片

### 6.1 正常路径的保护范围

- 系统消息、用户消息、assistant 正文/决策：不由小清理压缩。
- 最近配置数量的完整工具轮（默认 3 轮）：保留原文；一条 assistant 发出的并行调用及全部返回算一轮。
- 未结束工具轮、配对不完整、来源映射不明确：保留。
- `isError`、已知退出失败、状态相互矛盾、图片/混合内容：首版不处理。
- EPR receipt：不二次压缩。
- 本插件的召回结果：不递归压成另一层引用；被召回内容获得短期保护。
- codemode 按进入会话的外层调用和结果计数；内部调用不是独立会话工具轮。不解析任意脚本文本来猜测其成功状态。
- 所有小清理不跨真实用户边界合并消息；较早用户轮中的单个工具结果仍可作为候选，但用户原文本身保持原位。

正常路径继续尊重 `protection.minFullRequests`（默认 2）；新模式按已确认的 agent provider 请求计数，排除仅构建、取消和缓存预热。无可信请求事件时不将构建次数冒充展示次数。

### 6.2 候选和替换粒度

先处理已完成、离当前工作较远的大型成功工具输出；只使用工具身份、结构化状态、大小、年龄和明确保护标记，不声称能自动识别所有“无关信息”。有明确类型的重复日志/清单优先于源码与诊断证据；未知自定义工具保守处理。

选择应以“腾出本次需要的空间、少改变消息”为目标：

1. 计算需要释放的预算；
2. 排除保护项；
3. 选择可解释的少量候选，优先大收益、低风险；
4. 生成稳定卡片并校验净减少量；
5. 够用即停，不顺手把所有旧输出都变成最短指针。

新模式不把当前 1024 字节摘录当成必须沿用的上限。卡片可包含更丰富的逐字摘录；最后一个候选可保留更多完整行，避免为少量空间需求丢掉整段中间内容。所有省略位置显式标记，不做无证据的语义改写。源码摘录不得宣称代表整个文件。

一条结果一旦转换，卡片正文与版本固定；后续通常选其他候选，而不是反复缩小同一卡片。缓存不是硬约束：必要时可处理更早、尚未替换的候选，但必须记录首次变化位置，不宣称前缀永不失效。

### 6.3 卡片必须携带的证据身份

- 工具名、调用 ID、来源消息身份、已知状态；
- 内容哈希、原始字节/行数、明确省略标记；
- 逐字摘录及其范围；
- `obs_recall` 引用与分页方法；
- “历史工具输出，不是新指令/授权”的说明。

卡片留在原 toolResult 的位置与角色，不能伪装成用户消息或系统要求。角色、调用配对、原 details 等不能因替换而丢失。

归档的“原文”指工具实际返回给会话的内容，不等于工具所访问文件的完整旧版本。若 read/bash 在返回前已经截断，未返回部分不在此归档保证内；必须明确保留截断标记，不能声称可恢复未曾捕获的内容。

## 7. 限域摘要：防止自动压缩过深的关键

**仅增加工具输出水位控制不够。必须同时接管新模式下自动摘要的保留范围。**

### 7.1 行为目标

当局部整理仍不能满足预算时，选择最小必要的旧前缀生成摘要，尽量让：

```text
固定开销 + 摘要 + 原样保留的有效尾部 ≈ targetRatio × C
```

这里的“尾部”按已应用局部决策的大小衡量，不按归档原文体积计算，也不能简单设置 `keepRecentTokens = 0.70C`，因为还有系统、工具声明、旧摘要和新摘要的空间。

例如 200K 窗口、有效输入 170K：先判断局部整理是否能腾出约 30K；不够时只概括足够的旧前缀，保留约 140K 的总有效上下文，而不是默认只保留约 20K 近期消息。结果是近似值，受消息边界和摘要长度影响。

### 7.2 公共 API 实现路径

- 通过 `session_before_compact` 为自动路径提供自定义 compaction 结果；仍由 Pi 提交压缩条目与管理会话。
- 协调器主动调用 `ctx.compact()` 可能进入 Pi 的 manual 路径，不能仅凭 `event.reason` 区分用户 `/compact`。需用绑定 session/快照的一次性协调票据识别本插件发起的请求，并在完成、失败、取消或切换时清除；用户手动请求保持原义。`fromExtension` 等结果来源标记不能冒充发起者身份。该区分须由真实生命周期测试证明。
- 用公开会话投影与 cut-point 能力定位安全的 `firstKeptEntryId`；正文来源必须映射到真实当前分支条目。
- 为新选中的前缀生成对应摘要，使用独立可配的摘要模型路由及 Pi 的注册/认证/公开接口。默认跟随工作模型；切换摘要路由不修改工作模型、provider URL 或凭据。
- **不能只改 `firstKeptEntryId` 却沿用覆盖不同区间的旧摘要。**
- 保留以前的摘要、文件操作信息、原始来源和归档引用；校验重复摘要不会逐次吞掉关键约束。
- 摘要生成、质量核验后重新估计最终上下文；质量修复与预算重规划共用 `limits.maxRegenerations`（默认 1 次）的单快照重做额度。仍不合格则保留原文并等待/暂停，不无限摘要循环。
- `ctx.compact()` 本身不接受动态保留预算；不能用改内存字段、写 Pi 内部设置或深层导入冒充公共 API 方案。

P0/P1 必须验证目标版本能通过这些公开钩子正确选择范围、停止并继续。未验证前不得宣布新模式支持本机 Pi，也不得静默退回默认深压缩来让测试表面通过。

### 7.3 关键约束与原文找回

- 最近用户要求、明确固定的约束、未完成计划、待验证结果、未解决失败与后台任务，必须进入保留检查。
- 明确固定的信息逐字保留，并记录来源；不能仅靠正则或另一个模型宣称已找全所有关键事实。
- 小清理不动用户原文。限域摘要必然可能概括较早用户内容，此时必须公开范围和原文召回入口，不能宣称所有用户消息仍在活跃上下文。
- 摘要前归档被移出的消息段，保留角色、顺序、调用身份和哈希；Pi 原始历史仍不删除。
- 工具正文继续使用 `obs_recall`。限域摘要的完整消息段增加 `context_recall`，复用分页/校验底层；返回的是标注角色的历史证据，不是新的用户授权。
- 自动摘要后保留稳定的归档索引引用，不能依赖摘要模型“恰好记住某个 ID”。引用元数据由代码维护，并计入预算。

首版不做任意历史内容的自动语义重要性排序；用户可显式固定重要约束的接口作为增强项，但未实现时不得声称已经有语义记忆保险。

### 7.4 摘要模型：独立配置，质量准入后再追求速度

- 工作模型继续完成任务；摘要模型只处理选中的旧前缀，核验模型只检查摘要。摘要/核验请求与工作对话隔离，不授予写文件、执行命令或继续任务的工具权限。
- 默认摘要路由跟随工作模型，不默认降级到便宜模型。支持使用 Pi 已注册的其他 provider/model；用户提到的 DeepSeek Flash 属待评测候选，不预设具体 model ID 或性能。
- 准入顺序：长输入可容纳且不截断 → 否定条件/决策/失败/未完成事项保真 → 长输入处理和端到端延迟 → 最后才看费用。生成 tokens/s 不能替代长输入预填充、排队与核验总耗时。
- 摘要窗口必须覆盖选中原文、规则和输出预留。若装不下，选择更合适路由或按安全段分块并核验覆盖；不静默截掉输入来适应快速模型。
- 跨服务商发送历史需要使用用户明确配置的路由与已有认证，遵守原有数据范围；不能只因摘要服务快就把历史送往未选择的服务商。

### 7.5 质量门：通过核验才改变工作上下文

```text
冻结来源与受保护事项
→ 生成候选摘要
→ 确定性检查（来源/引用/状态/结构/完整输出）
→ 可靠模型对照原始选段做覆盖与矛盾核验
→ 重新检查快照与最终预算
→ 在安全边界一次性提交
```

- 所有模型生成的限域摘要均经过质量门；本地逐字摘录不额外调用模型。默认核验路由为工作模型，快速模型生成也不能取消核验。
- 明确固定的约束、关键数字/路径/命令、未完成计划和已知失败需有可追溯原文；区别“未运行”“失败”“通过”“推测”和“已验证”。不接受无来源的新结论或授权。
- 核验必须看到原始选段及受保护事项，不让模型仅凭摘要自评；截断输出、缺失引用或判断不明确都不提交。
- 摘要与核验各自做输入/输出预算检查；核验所需的原始选段、摘要和规则若装不下，改用合格路由或分段覆盖核验，不只截掉核验输入。
- 核验失败时，使用配置的核验路由重做；与预算重规划共用 §7.2 的重做上限（默认 1 次，可配置为 0）。额度耗尽仍失败时保留原文，在安全空间不足时暂停。
- 对高风险判断保留原句和足够上下文，不为了更短而改变条件、范围或来源角色。宁可多留证据，不要求摘要达到很高压缩比。
- 核验模型也会出错，不能将其“通过”当作无损证明；准入必须同时经过真实任务和早期约束回忆测试。
- 已验收摘要尽量保持稳定；若需要合并多次旧摘要，应回到相应原始归档和约束清单重建，不只将上一次摘要无限递归压短。输入过大时有界分段并保留覆盖索引。

### 7.6 可选后台预摘要：只准备旧前缀，不维护影子对话

首个功能闭环默认在安全边界按需生成摘要；后台是 P4 的可选体验增强，不是防止超窗的依赖。

仅在占用已进入维护区、预测局部整理可能不足，且资源允许时准备摘要。选中的旧前缀必须已闭合、避开当前活跃工具轮和明确保护项。每会话最多一个任务（包含生成、核验和有界重做），最多保留一项待处理需求，后续需求合并，不能每轮排一个摘要任务。

```text
开始准备： [固定旧前缀 A] [原样尾部 B]
用户继续： [固定旧前缀 A] [原样尾部 B] [新消息 C] [新消息 D]
验收提交： [摘要 A′]      [原样尾部 B] [新消息 C] [新消息 D]
```

A 的身份、正文哈希和归属未变时，用户继续三轮不必让任务失效；仅 leaf ID 改变不代表前缀改变。草稿只描述 A，不得恢复整个旧快照、丢掉 C/D，或声称已经概括了新消息。

任务状态为 `preparing → validating → ready → committed`，也可进入 `stale/cancelled/failed`。`ready` 只表示有可用草稿：仍须有实际空间需求，并在安全请求边界重新验证前缀谱系、保护项、模型/工具声明、待发消息、引用及最终预算。完成模型调用不等于成功提交。

- fork/tree、来源编辑、重叠压缩、会话关闭或用户取消时取消/废弃不适用结果；即使服务端不能取消，也不能晚到后修改当前会话。
- 前台有安全余量时正常继续；后台结果已过时则丢弃并合并后续需求，不反复阻塞前台等同一个旧草稿。
- 前台已无安全余量时，先做局部整理，再等待可用摘要或明确暂停；不能因为摘要慢而使用未经核验的半成品。
- 草稿、单次摘要/核验调用、重做与前台等待都有可配置的有限期限；超时保留原文并显示原因，不隐藏无限等待。后台总期限不因重试/进度更新重置，详见配置规范。
- 用户状态区显示“正在准备旧段摘要 / 等待空间 / 已提交 / 已取消”，不把后台进度当成新的对话消息。

资源调度以工作请求优先：不同服务商的独立资源通常较少竞争；同服务商仍可能共享 RPM/TPM/并发额度；本地同一 GPU 会争抢计算和显存。单会话限制之外，还要有进程级并发上限与跨会话配额协调。同 GPU 或共享限流影响前台时默认不并行运行，改为闲时准备或按需等待，不以节省摘要费用为理由抢占工作资源。

### 7.7 缓存策略：稳定提交优先，不追求摘要缓存命中率

- 不同 provider/model 默认按缓存隔离设计，不能指望摘要模型复用工作模型缓存；实际规则以 provider 为准。
- 即使是同一模型，摘要提示、序列化与片段起点也常与工作请求不同；见过相同文字不等于命中相同前缀。
- 本机 Pi 原生摘要 helper 设置 `cacheRetention: "none"`。复用它时不宣称已开启缓存；服务端自动缓存行为另行观测，不修改 Pi 核心强行打开。
- 一次性摘要正文低命中可以接受。固定摘要规则可保持稳定，但不为了命中率反复发送完整历史或维持第二份影子对话。
- 工作模型的缓存变化来自历史替换位置，与“摘要是谁生成的”是两回事。摘要通过全部检查后一次提交，不流式发布半成品、不每轮重写旧摘要。
- 缓存只服务于延迟与费用诊断，不得阻止必要证据保留或质量核验。

## 8. 突发输入保护与 Pi 原生压缩协调

### 8.1 为什么不能只改 context 钩子

本机 Pi 1.5.0 的轮间原生阈值检查可能先于本轮 `context` 处理。如果只在后者收短，原生摘要可能已经开始；如果只取消原生压缩，又可能把超大请求直接交给 provider。

必须在用户消息/附件入队、完整工具批次结束及最终请求发送前建立统一决策，并协调自动压缩入口；不能只在轮末检查工具结果。每次请求的安全检查独立于 70% 启动线，无论此前占用多少都执行。

### 8.2 控制顺序

1. **内容到达**：登记新用户消息、附件、工具结果和扩展注入；需要归档的原文异步保存，不修改 Pi 存储历史。
2. **候选请求形成**：合并本次真实待发内容，计算预算；生成带会话版本、模型、声明与待发消息指纹的计划。不能只靠旧百分比或增长预测放行。
3. **原生 threshold 入口**：若同一视图已有可应用且验证安全的局部投影，才取消不必要的原生摘要；否则提交已验收且仍适用的限域摘要、等待准备，或安全停止。
4. **context 投影**：应用已验证计划；存在异步等待时，提交前重新检查分支、正文哈希、配对、用户输入和取消信号。后台草稿不能直接覆盖整个会话。
5. **最终请求前检查**：校验包含晚到内容的请求预算，捕获工具声明、扩展注入和模型路由变化；异常则停止/重新规划，不发送已知超限请求。
6. **响应后**：用 provider usage 校准估计，记录误差。若仍发生 provider overflow，进入有界恢复；不将估计当成精确 tokenizer 保证。

不能把 `session_before_compact` 的取消当作安全证明。每个指纹下的修复尝试有上限；重复取消但没有进展时停下。`overflow` 是真实失败证据，不盲目取消重试；改走有界恢复。手动 `/compact` 不被压力策略偷偷取消。

某些 provider 或第三方扩展不能提供可靠的最后检查时机。此时只可标为“尽力维护”，不能宣称有严格容量保护；默认不启用声称全保证的高保留模式。最终事件顺序、取消语义和 load order 是发布门槛，不靠 monkey patch 解决。

### 8.3 新结果本身过大

正常的最近轮保护和完整展示次数是软保护，无法同时满足“无限大新结果完整展示”和“绝不超窗”。紧急路径：

- 先腾出旧候选，再考虑必要旧前缀摘要。
- 仍不够且新结果属于可归档的成功纯文本时，允许对该结果使用有明确提示的富摘录/分页引用；记录 `burst-admission`，不谎称模型已经看过原文。
- 当前失败诊断、用户输入、图片或未知语义不能安全降级时，暂停并要求分批、缩小输入或明确允许深压缩。
- 归档失败保留可用原文；若因此超出安全预算，暂停请求。**数据保留是 fail-open，超限请求发送是 fail-closed。**

不禁止并行工具，但按整批总量检查。增长预测和单次 read 的截断限额都不是整批预算保证。

## 9. 状态、归档与恢复

### 9.1 持久化内容

新增版本化状态，绑定 session、来源条目和分支谱系，而不是仅以当前 leaf ID 为命名空间：

- 策略版本与有效参数；
- 原文/卡片身份、已确认展示次数、稳定替换决策；
- 摘要范围与归档索引；
- 当前投影版本、失败原因及最后处理的边界。

决策可参考 OCC 的 public custom-entry 方式追加；归档与诊断位于 `runtimeRoot(ctx)` 派生目录，不开放任意存储路径或跨会话搜索。

### 9.2 提交与恢复协议

```text
生成候选 → 归档 → 完整性验证 → 持久化决策 → 应用投影
```

- 原文/元数据使用临时文件和安全发布策略，拒绝符号链接、非普通文件、哈希不符与不完整写入。
- 未完成归档不能产生有效占位符；状态缺失或损坏不得凭猜测恢复。
- resume 恢复已提交决策，重新校验归档。
- fork 仅继承当前分支允许引用的对象；从保留原文重建，或按经过验证的谱系复制必要归档。不扫描其他会话“找同名 ID”。
- native compact 后仍维护引用归属；专门覆盖“compact 后 fork，只剩摘要引用”的组合。
- 召回校验原文哈希与范围，中文/emoji/超长行连续分页可逐字节还原；任意 offset 的 UTF-8 边界规则明确。
- 旧对象格式保留读取兼容；新对象不得让 legacy 会话误读。
- 首版不自动 GC；容量不足先告警，无法归档时停止新增替换。后续清理必须先证明对象无活跃引用。

## 10. 性能与可观测性

先有正确性基线，再优化：

- 缓存来源身份、内容哈希、字节/行数和卡片，减少每轮重复拼接全文与读取归档。
- 对新消息增量索引；分支/compact/上下文编辑使相关部分失效。
- 同一次维护共用快照、调用表和 token 计量；只有实际改变时重新计量。
- 新归档与恢复分批执行、支持取消并让出事件循环；时间预算不是单个巨大同步任务的抢占保证。
- 原生快照复制和对新 context 副本应用既有占位符仍可能为 O(n)；不承诺整个流程 O(新增消息数)。

状态展示建议：

```text
Live Compact · retention
预计输入 74% / 软上限 80% · 最近3轮保护
本轮：旧工具结果 2 条 → 证据卡片，约释放 6K
原生摘要：未触发 · 归档：可召回
```

分别记录输入估计、真实 usage、保留原文比例、局部替换数量、摘要范围、首次变化位置、召回次数、耗时、误差、异常和暂停原因；体验指标另记摘要排队/生成/核验时间、有效提交率、过期丢弃率、前台实际等待时间与 P95 延迟。诊断默认只记 ID、计数、哈希和原因，不记录工具原文或凭据。预算数据不能伪装成美元节省。

Pi 原生状态栏可能使用上次 usage 或 canonical 投影估计，与本插件预计输入口径不同。高保留验收使用明确标注的预计请求与 provider 实际输入；不要求原生百分比每个瞬间都精确处于 70–80%。

## 11. 配置与兼容策略

**配置作为一等能力：水位、保护轮数、摘要/核验模型、后台开关与并发、超时、重做及本地批次预算均可配置。** 完整字段、默认值、校验、生效时机和测试清单集中在 [Live Compact 配置规范](live-compact-config-plan.md)，不在代码中散落硬编码阈值。

以下为常用配置示意，**当前 checkout 尚不支持，不可直接部署**；模型字符串是需要替换成 Pi 已注册值的占位符：

```json
{
  "version": 1,
  "observationPack": true,
  "onlineContextCompact": true,
  "evidencePreservingReducer": false,
  "liveCompact": {
    "enabled": true,
    "thresholds": {
      "startRatio": 0.70,
      "targetRatio": 0.70,
      "ceilingRatio": 0.80
    },
    "protection": {
      "keepRecentToolRounds": 3,
      "minFullRequests": 2
    },
    "summary": {
      "provider": "your-summary-provider",
      "model": "your-summary-model-id"
    },
    "background": {
      "enabled": false
    }
  }
}
```

- 比例关系为 `0 < targetRatio <= startRatio < ceilingRatio < 1`，最终安全预算优先。未配置的摘要/核验路由跟随工作模型，显式路由必须 provider/model 成对；工作模型本身仍由 Pi 管理。
- `liveCompact` 缺失/关闭时保持上游原义；新模式要求 ObservationPack 开启、EPR 关闭；OCC 可选，开启时关闭经济压缩；Action Fusion 不受影响。`cacheWriteReadRatio` 只保留旧模式含义。
- 单一配置来源和项目可信检查继续保留；项目文件替换用户文件，不跨文件合并。未知字段及非法类型仍报错，不增加 provider URL、凭据、shell、storage 或专用环境变量。
- 首版在扩展初始化时读取配置，修改后需重载扩展或重启；已有卡片保持稳定，新参数只影响新决策。旧后台快照不得在重载后提交。
- `/live-compact status` 显示配置/实际水位、摘要/核验路由、时限和降级原因；暂停维护只停止新决策，不关闭安全检查。
- 这是高保留 profile，不是原安装协议的 all-enabled profile。原 all-enabled 回归在新模式关闭时执行；正式安装采用哪个 profile 必须明确记录，不能偷偷忽略检查。
- 归档完整性、来源/角色/配对、摘要质量门、最终预算复核、同会话单任务及晚到结果隔离是强制底线，不提供绕过开关。

| 70% 加一批超大工具结果 | 实际批次检查生效；局部/限域摘要/暂停，不盲发超限请求 |

| 同尺寸篡改、截断、符号链接、磁盘满、权限失败 | 不用损坏对象替换原文、不静默返回伪原文 |
| resume / tree / fork / compact→fork | 决策归属正确、卡片稳定、引用可用且不串会话 |

| Pi threshold 先于本轮 context | 统一决策生效，不抢先触发默认深摘要 |
| provider overflow、摘要失败/取消 | 有界恢复；不循环、不假成功、不意外继续危险请求 |

| 摘要服务慢、限流或与工作模型共用 GPU/配额 | 前台优先、单任务；安全范围内继续，必要时明确等待/暂停 |

### 14.2 真实任务对照

至少四组，同模型、同 Pi 版本、同任务、同初始代码，记录实际配置和 provider usage：

1. 原生 Pi 默认压缩；
2. 原生 Pi 调整为相同提前阈值和较大保留尾部；
3. 上游 SoL-Pi，固定并公布机制 profile；
4. 本方案高保留模式，EPR 关闭。

组 4 进一步比较：摘要跟随工作模型 / 独立快速模型，以及后台关闭 / 开启。保持工作模型和初始任务一致；核验路由、输入范围、质量门槛、并发与缓存条件必须记录。DeepSeek Flash 只是候选名称，具体可用 model ID、窗口、速度和保真能力待所用服务商实测。

任务包括大仓库阅读、长日志调试、并行文件加载、重复失败修复、长会话早期约束追问、摘要后引用原始中段证据，以及模型窗口切换。每类至少 3 次只作为试用信号，不宣称统计显著。

按顺序评估：① AI 性能——任务测试/约束是否完成、错误是否被掩盖、早期信息回忆、精确召回与无来源结论；② 用户体验——前台 P95 等待、卡顿/暂停频率、后台有效提交率、正常继续成功率；③ token/费用——仅诊断。活跃原文保留率、摘要范围和 70–80% 水位用于解释质量与体验，不能独立替代它们。

**不以 token 最少、压缩比例最大或上下文数字最小作为胜出标准。** 质量出现稳定退化就收紧对应策略；不能拿费用下降掩盖丢约束。

## 15. 非目标与已知限制

- 不修改、fork 或 vendor Pi；不注入 DSH preset；不新增代理后端。
- 不保证无限长历史全部留在有限窗口内，也不保证模型会主动召回所有需要的细节。
- 小清理不自动处理失败诊断、图片、未知结构化字段或 assistant 推理内容；限域摘要对受保护事实另做保留检查，不能将摘要等同于完整原文。
- 不把缓存地板置于信息与安全之上；不承诺零缓存失效。
- 不修改 provider URL、凭据、主模型或 shell；不记录秘密。
- 不自动删仍有引用的归档；不把整份目录容量估计当硬磁盘配额。
- 不将预测当容量保证；未验证的 provider/扩展组合不得标为严格安全模式。
- 不将本方案的预期收益描述为已经跑出的测评结果。
