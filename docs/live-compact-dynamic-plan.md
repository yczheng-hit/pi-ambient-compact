# Live Compact 下一阶段：按水位触发的全局选择性压缩

状态：G0（接口与恢复可行性）已完成并有自动化测试，结论见 §10 G0 完成记录；G1–G4 尚未实现。对照基线为 `main` 的 `79a3e2e`。本方案不修改用户配置或缓存设置。

继续开发全局 AI 压缩时先读本文。本文取代 [原方案](live-compact-plan.md) 中“持续维持 70–80%”“主要摘要必要旧前缀”的下一阶段目标，不改变原方案记录的 P1 已实现事实。[现有配置规范](live-compact-config-plan.md) 仍描述当前实现；本文新增字段均不可直接部署。

## 1. 本轮确定的目标

优先级仍是 **AI 性能 > 用户体验 >> token 开销**。数据完整性、授权边界、容量安全是底线。

- 约 70% 是进入维护的门槛，不是压缩后的保留指标；不为凑到某个百分比删除有用证据。
- 在达到门槛后，集中审阅整个有效上下文，选择低价值片段压缩；不只按“最旧”排序。
- 重点处理重复监控、重复查询、已完成阶段的长记录，以及占用很大的旧 assistant 工具调用参数。重要约束、状态变化、未解决问题和近期工作保留。
- 700K → 300–500K 可以是合格结果；若必要工作集需要 600K，也应接受。数字是结果，不是强制压缩率。
- 接受一次维护后的缓存重建；减少的是频繁小改和重复摘要，不是拒绝一切缓存失效。
- 保持现有缓存默认行为：不改 `promptCache`、`PI_CACHE_RETENTION`、`cacheWarming` 或 `showCacheMissNotices`，不等待推测中的缓存过期，不暂停既有续期策略。
- 首版按需、前台安全边界执行；不增加常驻摘要 AI，不因每次定时唤醒调用模型，不默认启用后台预摘要。

## 2. 当前本地实现与差距

| 项目 | 当前代码 / 配置 | 下一阶段 |

## 3. 一个协调器、一个维护批次

```text
收到输入 / 工具批次完成 / 即将发请求
                ↓
      实际候选请求预算与轻量索引
                ↓
  低于启动线：只追加，不调用压缩 AI
                ↓ 达到启动线且值得维护
      冻结快照、建立安全片段和保护集合
                ↓
   AI 输出选择计划 + 被选片段的摘要
                ↓
    确定性校验 → AI 对照原文核验
                ↓
     归档 → 快照/预算复核 → 批量提交
                ↓
       固定已提交内容，继续追加历史
```

### 3.1 触发与冷却

- `startRatio` 默认仍建议 0.70，但到达它不等于每轮都调用模型。
- 建立便宜的片段索引：大小、角色、完整工具轮、历史阶段、已整理标记、可能重复的指纹。索引只能判断是否值得评估，不能仅凭重复文本自动删除内容。
- 动态策略建议参考目标 `targetRatio = 0.50`，软紧迫线 `ceilingRatio = 0.80`。目标是偏好：不压过头以追求数字，也不因结果仍为 0.60 就自动拒绝。
- 普通维护建议至少回收窗口的 10%（不是输入的 10%）；以编排后的真实候选估算复核。例如 C=1M 时，700K→600K 可接受，700K→680K 通常不值得提交。
- 上次尝试后至少间隔 12 次真实工作请求；若上次失败/收益不足，还需新增约 5% 窗口的输入再重试。压缩 AI、缓存预热和仅构建请求不计为工作请求。
- 无可回收片段时不调用模型；同一快照的“无收益/失败”结果持久化，重启不能清空冷却而重试。
- 到 80% 或预计本次输入接近安全上限时，可以越过冷却、最低回收收益限制，但不能越过保护和质量门。对同一失败快照不无限重试；确实无法继续时暂停并给出原因。
- 新用户消息、模型切换、分支切换、原生 compaction 等使相关任务失效；重新估算，不用旧模型的增长量或校准值。

这些数值是待验证的建议，不是已测出的最佳参数。正常任务中应有多轮纯追加阶段，而非压缩后每轮重写。

### 3.2 常驻循环的性能预算

- 低水位仅更新增量计数和片段索引；不遍历所有归档文件、不算所有大文本哈希、不调用模型。
- 只有进入维护批次后才冻结较大快照、哈希选中片段、做完整预览。
- 模型调用异步等待，并显示进度与取消入口；“不阻塞 Node 事件循环”不等于“前台任务不用等”。首版维护期间主请求等待是明确行为。
- 本地 `batchBudgetMs` 限制的是分批扫描/归档的让出时机，不是单个 I/O 或整个模型维护的硬时限。一次维护可以分批准备，最终统一提交。

## 4. 全局选择，但不要求 AI 重写几百 K 上下文

### 4.1 安全片段与来源

代码将有效投影组织为带稳定 ID 的片段，记录原始 entry ID、投影哈希、角色、时间、工具调用闭包、是否已摘要和保护原因。最近 N 个完整工具轮、不完整调用和不明来源片段始终保护；重复调用 ID、缺结果、混合内容不得猜测配对。

默认允许：

- 已完成阶段里的 assistant 冗长说明；
- 已完成的 assistant 工具调用 + 对应全部结果；
- 多次重复监控的检查过程和无变化结果；
- 已存在的工具卡片：只有拿到原始归档并纳入核验时才能再次总结，不能反复摘要上一版摘要。

首版默认保留原文：

- 真正用户消息、任务约束与授权；系统/工具声明；
- 当前未完成工作、最近 N 轮、刚召回的证据；
- 失败/状态不明的诊断、图片和未知混合内容；
- 仍会被现有工具/扩展依赖的状态与来源元数据。

`pi-scheduler` 当前用 `sendUserMessage()` 发唤醒：仅凭 `⏰ 定时任务…` 或重复文本不能证明它不是用户指令。首版保留这些 user 消息，压缩它们对应的旧检查过程/结果。若以后希望连唤醒消息也合并，需要 scheduler 提供可信的任务/唤醒/消息 ID 关联；另行授权和集成，不靠正则扩大删除权限。

### 4.2 模型只输出变更清单

输出结构包括：`snapshotId`、选中的 `segmentIds`、处理方式、摘要、关键事实的来源 ID、保护/保留说明。处理方式为保留、逐字摘录、片段摘要；未列出的内容默认原样保留，不提供无来源的任意删除操作。

模型不用回传保留的 300–500K 原文。代码按引用拼装未变内容，仅替换核验通过的选段。这限制输出长度、减少误改并保持原文及工具声明字节稳定。

全局选择允许多个不相邻片段，但每段摘要在对应历史位置承载，首版不跨真实用户消息重新排列历史，不把过去发生的事件挪成新的用户指令。

### 4.3 定时监控的保留标准

AI 在维护时分析整组检查，保留检查对象、时间范围、状态变化、异常、最后一次确认状态、未解决事项及原文引用。不能把“相同回复第一行”当成无变化证明；日志正文可能含关键进展或失败。

不增加每次唤醒的摘要调用，也不假设定时任务都无用。提醒文本或第三方输出不能变成新的授权。

## 5. 模型路由与质量门

- 复用 `summary.provider/model` 与 `verification.provider/model`；省略时跟随工作模型，在任务开始时冻结有效路由。
- 迁移到动态策略时列出实际摘要/核验服务商以及将发送的历史范围；跨服务商只使用用户明确选定的路由。不因失败、速度或窗口不足静默换到另一个服务商。
- 使用 Pi `modelRegistry` 的公开调用和认证。EPR 的 provider 调用可作为实现先例，但不启用 EPR、不直接复用其完整行为（例如不能把 `stopReason: "length"` 的截断结果当成合格摘要）。
- 默认一批 **一次规划/摘要生成 + 一次核验**。本地逐字摘录不额外调用 AI。生成失败或核验失败最多按 `limits.maxRegenerations` 有界重做，调用数还受整批上限与总时限约束。
- 压缩模型没有写文件、执行命令、下单、调度等工具权限，只产出结构化数据。
- 生成调用检查整个选定上下文能否装下。核验对照被改片段的原文、候选摘要、任务约束与必要相邻上下文；未变部分用哈希和引用核对，而不是再让模型输出整份新历史。
- 必须核验否定条件、数字、路径/标识、状态变化、未解决问题、来源角色，以及“计划 / 尝试 / 成功 / 未验证”的区别。
- 两个模型各自检查输入窗口和输出额度；不能以“速度快”为理由给小窗模型静默截输入。首版要求所选路由能容纳对应完整输入，不自动开启分层摘要；装不下时提示更换合格路由或暂停。分层摘要后续独立增加覆盖账本与调用预算。
- 核验模型也可能漏错，因此归档和召回始终保留；真实任务质量必须另做对照，不把自动核验当作无损证明。

## 6. 提交、归档与恢复

### 6.1 复用 context_edit，但增加整批校验

在公开 `turn_end` / `agent_before_settle` 等可操作边界提交；保留其他扩展已有 `event.entries`，不能覆盖别人的提案。需要更早的准入阻断时先停止请求，在经验证的维护路径上提交，不往用户提示文本里塞一个伪“维护指令”。

提交前要求：

1. 片段和来源仍在当前分支，内容哈希、模型、配置、保护集合、待处理输入均匹配快照。
2. 所有被省略的 assistant 调用和工具结果配对闭合；摘要不带可执行的旧 toolCall、虚构权限或新 role。
3. 摘要只采用 G0 验证过的两种放置方式（§10 G0 完成记录第 1 条）：跨完整轮次时，写进这段的第一条 assistant 消息；一轮任务中途时，写进保留的第一轮工具结果。其余被覆盖的记录用 omission。不得把摘要改写成 user 或 system 角色来提高可信度；其他结构一律由校验器拒绝。
4. 全部原文、压缩前的有效投影和变更清单已成功归档。
5. 预览后的请求在真实输出预留及安全余量下可发送；没有为了满足目标丢弃保护内容。
6. 批次提交后不改摘要，后续原文继续追加。UI 指标只能在确认提交后计为“已压缩”，不能把已准备草稿计成效果。

### 6.2 不能把批量草稿当成原子事务

Pi 1.5.2 的 `emitBoundary()` 会预览整批，但 `_applyBoundaryDrafts()` 逐条写入；官方文档明确持久化不是事务。

因此 `commit.ts` 必须有批次 ID、预备清单、完整原文、提交回执与幂等恢复。部分落盘、磁盘失败、崩溃重启时，未完整批次不能进入下一次 provider 请求。优先通过公开接口恢复/补偿；如果无法安全自动恢复，就停止请求并提供恢复入口，不直接修改 Pi 会话日志。

这是 G0 的发布门槛，不预先声称已解决。若公开接口无法实现可靠恢复或准入阻断，先只提供预览，不上线自动全局编辑；不 patch Pi 来绕过。

### 6.3 新增 context_recall

`obs_recall` 保持兼容；新 `context_recall` 分页返回完整消息片段，带原始角色、entry ID、调用 ID、时间、哈希与归档链路，并明确是历史证据而非新指令。

新归档继续放在 Pi 会话派生的 `sol-pi/<session-id>/` 下。恢复、fork、tree、原生 compact 后引用仍要可用；对象缺失时只从当前分支可证明的源记录重建，不能遍历其他会话找一个同名内容。新模式不得自动删除仍被引用的归档。

## 7. 请求安全与原生压缩协调

### 7.1 修正现有安全预算

当前 `budget.ts` 将输出预留限制为 `min(model.maxTokens, 32768, C/4)`。这只能算当前维护策略的估计，不能证明真实请求安全；如果本次输出允许 128K，不能只按 32K 预留。

新准入必须用本次实际有效的输出上限；取不到时采用可证明保守的上限，并显示预算来源。计入系统 sections、真实工具声明、用户附件、整批工具结果、额外注入、估算误差，以及模型切换后的窗口变化。

现有 chars/4 与固定图片估算也不是所有语言、provider 的严格上界。要记录估算置信度，结合可用 tokenizer/服务端计数、真实 usage 和保守余量；能力未知时报告“预算未验证”，不能用校准比例的上限冒充安全证明。

Pi 原生阈值 `C - compaction.reserveTokens` 是另一条线；它与输出预留、Live Compact 的 80% 软线不是同一概念，状态显示与文档不再混称。

### 7.2 不能靠 throw 阻断

已核对的 `runner.emitBeforeProviderRequest()` 会捕获扩展异常、报告后继续；`turn_end` 返回 `continue: false` 也不能抑制自然继续。因此，仅抛异常、取消一次原生压缩或设置 continue:false 都不是可靠容量闸门。

G0 要验证 `input`、启动前、完整工具批次后、`context_with_system`、最终 provider payload 与 `ctx.abort()` 的实际顺序和取消传播。对每个支持的 transport 断言“禁止发送时 provider/transport 实际发送计数为零（不能只检查本地抛错）”；发生在主循环之外的摘要请求也要有自己的准入。缺最终钩子或晚加载扩展仍可改 payload 的组合必须明确标为不支持严格准入，不能默默启用全保证模式。

### 7.3 pi-compaction-guidance 的竞争

该本地扩展同样监听 `session_before_compact`，会主动生成摘要。Pi 的规则是最后一个非空结果覆盖前面的结果，而 `cancel` 立即短路。所以只在 SoL-Pi 后置返回自定义摘要，既可能被覆盖，也可能先白跑另一份摘要。

首版动态模式要求明确的自动压缩所有权：优先让 SoL-Pi 在该扩展之前拦截自动入口，并同时确保取消后的请求不会继续超限；也可在后续经授权的协作修改中让 guidance 对动态模式自动路径让位。未证明共存时拒绝开启动态策略并给出安装诊断。本任务不擅自修改外部扩展或它的配置。

用户手动 `/compact` 不被偷偷接管。SoL-Pi 自己发起的维护若经过 manual 路径，必须使用绑定会话/快照的一次性协调标识，不能把 `reason: manual` 或 `fromExtension` 当作可靠发起者身份。

## 8. 配置和兼容迁移

新增显式策略：`liveCompact.strategy` 为 `local-tools` 或 `dynamic-ai`，缺失时继续使用当前 `local-tools`，不让现有用户突然承担模型调用、改变压缩深度或外发范围。

建议的动态策略配置（**未实现，不能直接使用**）：

```json
{
  "version": 1,
  "actionFusion": false,
  "observationPack": true,
  "evidencePreservingReducer": false,
  "onlineContextCompact": true,
  "liveCompact": {
    "enabled": true,
    "strategy": "dynamic-ai",
    "thresholds": {
      "startRatio": 0.70,
      "targetRatio": 0.50,
      "ceilingRatio": 0.80
    },
    "protection": {
      "keepRecentToolRounds": 3,
      "minFullRequests": 2
    },
    "maintenance": {
      "minSavingsRatio": 0.10,

      "retryGrowthRatio": 0.05,
      "maxCallsPerCycle": 4,

}
```

- `targetRatio` 在 local-tools 中保留旧语义，在 dynamic-ai 中为软参考目标；所有显式配置值均保留，不偷偷覆盖用户原来的 0.70。迁移时展示差异，用户确认后才改文件。
- 建议 dynamic-ai 内置 target 默认 0.50，local-tools 仍为 0.70；模式选择必须先于补默认值。维持 `0 < target <= start < ceiling < 1`。
- `maintenance.minSavingsRatio`、`retryGrowthRatio` 都以模型窗口 C 为分母，有限数值且在 [0,1)；cooldownRequests 为 0–1000 的安全整数；maxCallsPerCycle 为 2–8 的安全整数；timeoutMs 为 1000–1800000 的安全整数（毫秒）。未知嵌套字段一律拒绝。
- `maxCallsPerCycle: 4` 表示通常生成+核验两次，失败后至多再生成+核验两次；与现有 `limits.maxRegenerations` 取更严格约束。总时限覆盖两种调用、重做及其网络重试，不因重试重置。
- 动态模式的本地收短和 AI 片段摘要共用一个快照、一个最终提交；不能先单独跑 8 个局部替换，再立即跑一次全局压缩，产生连续两次历史改动。
- 不使用定时器每隔几分钟运行维护，不用 `cacheWriteReadRatio` 驱动新策略，也不修改 Pi 的缓存设置。
- 首版只在验证过的 Pi/provider/扩展组合支持动态策略。开发基线仍是 Pi 1.5.2；本机此前的 1.5.0 API 探测不能替代新生命周期验证。旧策略和已关闭模式保持原兼容范围。
- CLI preflight 与运行时共用 schema，显示有效策略与尚未完成的路由/容量/扩展共存验证。通过 JSON 校验不等于动态模式已可运行。

## 10. 分阶段交付与验收

### G0：接口与恢复可行性（先做，不写完整 AI 管线）

沿用 `agents-install.md` Phase 1 建立当前基线。在真实 Pi AgentSession + faux/受控 transport 中验证：

- 中间完整工具轮可以安全替换/省略，原始记录不变；Claude 与 Codex 类型的调用/推理块不会拆坏。
- 在需阻断时 provider/transport 的实际发送计数为零，取消后不自动恢复，不丢新用户输入。
- 多条编辑部分落盘、重启、重新加载、fork 后不会发送半批次。
- 与 pi-compaction-guidance 的两种加载顺序均有确定行为；不支持的组合被明确拒绝。

完成标志：上述路径都有可重复证据。不能成立就暂停后续自动提交实现，只交付预览；不修改上游 Pi。

**G0 完成记录**（`tests/live-compact-g0.test.ts`、`tests/live-compact-validator.test.ts`；Pi 1.5.2，真实 AgentSession + faux provider；Anthropic 与 OpenAI Responses 请求体由本机回环服务截获，不访问外部网络）：

1. **中部完整片段可以安全替换／省略。** 已验证两种摘要放置方式，最终请求体中角色严格交替、工具调用与结果一一配对、没有合成错误结果，原始记录不变，重新打开会话文件后投影一致：
   - **跨完整轮次**（两条用户消息之间的整段）：把摘要写进这段的第一条 assistant 消息，其余省略，得到 `[用户][摘要][用户]`。
   - **一轮任务中间的连续工具轮**：保留第一轮的调用（参数可压缩），把摘要写进它的工具结果，其余省略，得到 `[调用][结果=摘要][下一条 assistant]`。
   这两种结构都不会产生连续 assistant 消息。其他结构必须经校验器拒绝，不能依赖 provider 合并。
2. **pi-ai 会给缺结果的工具调用补一个“No result provided”错误结果**，相当于向模型谎报工具失败；缺调用的工具结果则不修复，provider 会拒绝。两者都由 `validator.ts` 在提交前拦截。
3. **两个已验证的提交时机：** `turn_end`（任务中途；下一次请求即使用新上下文）和 `agent_before_settle`（任务结束；不额外发请求，下一条用户消息的第一次请求即使用新上下文）。
4. **能可靠阻止请求的只有两种方式：** 在 `turn_end` 调用 `ctx.abort()`（已核对 provider 实际调用数不再增加，之后会话仍可继续使用）；`input` 返回 `handled`（不会启动任务）。**无效的方式：** `before_provider_request` 抛异常（Pi 记录错误后照常发送）；`turn_end` 返回 `continue: false`（不抑制自然的下一次请求）；取消原生压缩（请求仍然带着完整上下文发出）。
5. **批次：** 只要有一条编辑无效，Pi 就拒绝整个提案，什么都不写入。但落盘不是事务，因此采用“开始标记（含完整编辑清单）→ 编辑 → 结束标记”的写法，并按**先省略工具结果、再省略 assistant 消息、最后替换内容**的顺序写入。已逐个前缀验证：任意中断点都不会出现孤立的工具结果或连续 assistant 消息。按“先替换”排序会出现孤立结果，已用反例测试固定这一点。模拟崩溃后重新打开会话，能识别出未完成的批次，并在下一个边界补全（结束标记带 `recovered`）。
6. **残余风险：** 从崩溃到下一个边界之间的那一次请求，被省略结果的调用会带上合成错误结果。G3 需要在 `context` 钩子里先在内存中补全，或者在补全之前阻止请求。
7. **原生压缩所有权：** 对 `session_before_compact` 返回 `cancel` 会立即短路，两种加载顺序下最终都不会写入 compaction。但如果另一个压缩扩展先加载，它会先执行完自己的工作（pi-compaction-guidance 会调用一次模型），之后才被取消。在本机的包列表中，pi-compaction-guidance 排在 SoL-Pi 之前。因此动态模式需要把上下文保持在 Pi 原生阈值以下，避免触发原生压缩；必要时建议调整加载顺序。另外，取消原生压缩本身不能代替请求准入。
8. **尚未覆盖：** 带签名的推理块（Anthropic thinking、Responses reasoning）在真实服务商上的回放，以及 nvidia-inference 等代理是否接受这些请求，只能在 G4 用真实服务商验证；离线转换会丢弃跨模型的推理块，验证不了这一点。

### G1：配置、片段索引与维护状态机

实现 strategy 迁移、片段/保护图、真实请求增长与冷却、快照和预算。先用确定性假计划。

验收：低于启动线零摘要调用；连续几十次唤醒不会各调一次模型；无收益快照不反复重试；重启不能清空失败记录；切换模型后预算和状态正确。

### G2：全局选择、摘要与质量门

接入两条已配置路由，只产出预览，不自动改历史。通常两次调用，有界重做。首版完整输入必须适配模型窗口。

验收：关键约束、失败状态、数字、任务进展与来源在摘要中可核对；注入内容、截断输出、错 ID、跨分支、保护片段被改、空摘要均拒绝；全局规划不回传所有未变原文。

### G3：归档召回、整批提交与准入

G0 能力门通过后接入真实提交；原文先归档、提交后计数、跨 fork/重启可召回；自动原生深压缩由协调器接管，失败保留原文并安全暂停。

验收：拒绝的计划上下文完全不变；同一批次不重复应用；partial-write 故障不泄漏到 provider；大粘贴/并行工具结果/晚注入/模型变小仍有准入保护；用户手动 compact 行为明确。

### G4：质量、延迟与缓存对照

对比原生 Pi 默认、原生大尾部、现有 local-tools、新 dynamic-ai；工作模型、任务、初始代码一致。

至少包括：

- 700K 左右上下文中，大量中间监控重复但夹有一次关键状态变化；变动保留，不要求压到固定大小。
- 大量 assistant 工具调用参数但单条 toolResult 很小；新方案不能继续只清理大 toolResult。
- 无低价值片段；不为了达到 50% 强删，报告无法达到目标。
- 连续工作不超 TTL；仍能在必要时维护一次，之后多轮只追加；无需等待缓存冷却。
- 摘要模型小窗、核验超时、取消、切换到 Codex / 非 Codex、reload、fork、原生 compact，以及 scheduler 的不可信文本标记。

评估顺序：任务正确性/约束与证据保留 → 整理次数与端到端等待 → 请求安全与恢复证据 → 缓存/token 诊断。安全是发布门槛，不参与成本折中。延迟拆开记录生成、核验、归档/提交、第一次工作请求预填充及后续请求；缓存只能由 provider usage 证明，faux 测试不能代替真实命中率测量。

G0–G3 全部通过才形成动态压缩功能闭环；G4 通过后才推荐替换日常 local-tools 配置。后台预摘要和小窗口分层压缩不在首版范围。
